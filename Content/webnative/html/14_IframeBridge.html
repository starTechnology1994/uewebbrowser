推荐方案: PostMessage 桥接
无论 iframe 是同源还是跨域,统一使用 postMessage 进行通信。这是唯一一种在所有场景下都安全可用的方案,也是本 Demo 的默认配置。

1. Same-Origin 模式

iframe 通过 webnative:// 自定义协议加载, 与父页面同源。子页面可直接访问 window.parent.WebNative API。

优点: 零桥接开销,调用最直接。

缺点: 仅限 webnative:// 协议页面,不支持第三方 iframe;安全隔离弱。

2. Cross-Origin 模式

用 data:text/html,... 创建独立 origin 的 iframe, 浏览器阻止其访问 parent.WebNative。 子页面必须通过 postMessage 与父页面桥接。

缺点: data: URI 功能受限(无 localStorage,部分 API 不可用)。

3. PostMessage 桥接 (推荐)

统一的消息通道: 子页面所有通信都通过 window.parent.postMessage({action, name, body}, '*') 发送, 父页面监听 message 事件中转 UE。

消息协议:

  • action: 'toUE' — iframe → 父页面 → UE
  • action: 'fromUE' — UE → 父页面 → iframe
  • name — 消息名称 (如 'FromIframe')
  • body — JSON 字符串,需 JSON.parse()

优点: 跨域安全,统一接口,任何 origin 的 iframe 都能通信,适合生产环境。

完整通信链路

子页面 → UE:

iframe: send(name, data) → postMessage({toUE}) → 父页面 message listener → WebNative.send(name, body) → UE

UE → 子页面:

UE → WebNative.on(name, ...) → 父页面 frame.postMessage({fromUE}) → iframe message listener → 子页面处理

安全建议
  1. 生产环境将 postMessage(..., '*') 改为指定 origin。
  2. 接收端校验 e.origin 防止恶意站点注入。
  3. body 必须是合法 JSON,不符合格式的消息会被丢弃。
